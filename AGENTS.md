# Repository guidance

## Canonical package and catalog metadata

The canonical distributable plugin package is `plugins/token-max`. Root-level compatibility files and client manifests aren't additional plugin capabilities. Keep curated marketplace metadata in root `catalog-info.json`, outside the package archives. Keep the skill description in `plugins/token-max/skills/token-audit/SKILL.md` frontmatter.

Review `catalog-info.json` when a maintainer adds, removes, or renames a skill, or changes its frontmatter description or behavior. Review it when a command or hook action changes, or when a Model Context Protocol server or tool changes. Update examples, prerequisites, expected results, platform invocations, and source selectors when supporting documentation changes. Review platform support, installation guidance, runtime requirements, and changelog status. Use repository-relative paths and selectors. Keep curated prose human-reviewed. CI validates the sidecar but doesn't generate claims or rewrite it. The native inventory lists components and determines counts. Mark support `not_documented` without source evidence. Leave `changelog` null when no changelog exists, so the marketplace can use GitHub Release notes. Preserve report-only behavior and keep default in-app review free of terminal setup requirements. Keep optional local collectors separate. Don't claim demonstrated net savings. Describe fix prompts as illustrative guidance. The plugin doesn't execute them.

Validate locally with `python3 -m pip install -r requirements-catalog.txt` followed by `python3 scripts/check_catalog_info.py`. The validator checks the vendored `.github/schemas/upstream-info.schema.json`, repo-relative source paths, Markdown headings, CSS selectors, platform evidence, and native capability references. To refresh the schema, first confirm a newly approved marketplace schema revision, copy that exact schema into `.github/schemas/`, update the pinned secure hash digest and marketplace commit in `scripts/check_catalog_info.py`, then update this procedure and test the resulting metadata in a reviewed PR. Never follow a moving schema branch in CI.

Catalog maintenance procedure: edit the sidecar in a reviewed PR when a listed source area changes. Run the validator and relevant checks. Obtain review, merge the PR, and tag the release commit. Pull request checks and the tag release workflow validate the exact checkout before packaging or publication. CI fails closed on stale metadata. CI must not rewrite or push catalog changes. Release notes generated by GitHub are the fallback while `changelog` is null.

## Change quality

- Preserve the report-only audit boundary: don't edit projects, apply fixes, install tools, or change configuration during a review.
- Keep default in-app review independent from optional local collectors. Collectors run only when requested and supported.
- Don't claim measured savings without evidence. Describe fix prompts as guidance, not executed work.
- Don't commit credentials, environment values, local user paths, private logs, session contents, or sensitive collector output.
- Keep Claude and Codex manifests and release archives consistent with their intended package contents. Don't count compatibility copies as capabilities.
- Update relevant documentation and catalog metadata when behavior, interfaces, platform support, or prerequisites change.
- Keep diffs focused, preserve unrelated work, and run relevant tests, site checks, package checks, and the catalog validator before committing. Report precisely what ran and what remains unverified.
- Author commits as `swackhamer` and verify each signature before requesting review.
